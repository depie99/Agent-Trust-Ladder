THE CONTRACT

What this bridge guarantees.

Source of truth

.trust/manager/feed.jsonl and the provider session logs under .trust/manager/overnight/<task> remain authoritative. Codex history is a provider-facing projection, not a replacement for ATL state, evidence, or gates.

Sync behavior

Each completed run, overnight, or launch session leaves its feed and transcript material for the bridge; codex bridge sync imports it — manually, or automatically where the runtime session hook is wired. Checkpoints make repeated syncs idempotent, so only new material is injected.

ARCHITECTURE MAP

One source, two Codex surfaces.

The local feed and provider transcripts stay authoritative. The bridge builds an incremental context item, records a checkpoint, and chooses the safe Codex surface: a token-free dedicated history thread or an explicit visible queue turn.

01 · RECOMMENDED

Create a dedicated ATL history thread.

This is the token-free path. ATL creates a persistent Codex thread, names it ATL Team History, and imports context with thread/inject_items. It does not start a model turn.

PowerShell
node runtime/atl-manager.mjs codex bridge start
node runtime/atl-manager.mjs codex bridge status
node runtime/atl-manager.mjs codex bridge sync

The command prints the created thread id and a codex://threads/<id> deep link. The desktop app can open that thread, while ATL keeps the local feed and transcripts as the durable source.

02 · DAILY OPERATION

Inspect status or import one task.

PowerShell
node runtime/atl-manager.mjs codex bridge status
node runtime/atl-manager.mjs codex bridge sync
node runtime/atl-manager.mjs codex bridge sync --task T-004
node runtime/atl-manager.mjs history --source codex --n 10

The bridge records per-thread feed and log cursors in .trust/manager/codex-bridge-state.json. A second sync with no new feed or transcript returns no new context instead of duplicating the previous import.

CHOOSE THE SURFACE

Projection, rollover, or visible turn?

ModeWhat happensCost / trade-off
dedicatedInjects assistant context into an ATL-owned persistent thread.No model turn; model-visible context.
new-thread fallbackIf the desktop opens the target and owns its writer lock, ATL creates the next history thread and updates the target.No model turn; history is split across rollover threads.
queueQueues a normal message into an exact existing Codex session.Visible user turn; model usage and response cost apply.

Use queue only when the exact current desktop conversation must contain a normal chat message. The automatic fallback never selects it silently.

03 · EXACT CURRENT CHAT

Use the visible queue transport deliberately.

To put an import into one already-open desktop conversation, link that thread with --mode queue. This is the only supported path in this repository that intentionally creates a normal visible turn.

PowerShell
node runtime/atl-manager.mjs codex bridge link <CURRENT_THREAD_ID> --mode queue
node runtime/atl-manager.mjs codex bridge sync --task T-004
Token boundaryEvery queue import starts a model turn. Do not enable it as a background default unless the owner explicitly accepts the usage and the extra model response.
WHY THIS SHAPE

Ownership and failure boundaries.

Why not write the rollout file?

Codex persists thread metadata and history through its app-server/session store. Directly appending JSONL while the desktop owns a writer can race the store, leave metadata stale, or corrupt the conversation. ATL does not use that shortcut.

Why does rollover exist?

The desktop app may keep the currently open thread's writer lock. An external app-server process can still create and persist a new thread, so ATL rolls forward instead of silently dropping the update or starting a paid turn.

Official protocol boundarythread/inject_items appends prebuilt Responses items without starting a user turn. codex queue queues a text message for an existing session and therefore follows the visible-turn path. See the official app-server documentation ↗ and developer commands ↗.
