# Plan Studio contract

## Apply the contract

Follow [Plan Studio](plan-studio.md) to generate, clarify, review, and approve a plan. Inspect the current artifact, source revision, and review binding before approval. If validation fails, update the artifact and obtain a fresh review rather than retrying stale evidence.

Plan Contract v2 separates requirements, constraints, observed evidence, assumptions, open questions, acceptance examples, and risks. Every task links to requirements and records instructions, deliverables, prerequisites, affected paths, completion checks, a verifier, and a reason for each selected skill.

Generated plans remain proposals. Approval requires a separate provider review with no unresolved consequential questions or major/blocker findings. The review is tied to the plan, original intent, and fingerprints of referenced files; editing a task or changing captured evidence clears its readiness. Local templates and legacy drafts remain useful for editing but cannot be approved as reviewed implementation plans. When `egmReview.policy` in `config/manager.json` requires a deep review (`requireDeepReview` with complexity, task-count, or touched-path thresholds), approval of a matching plan additionally demands a fresh passed EGM review — an accuracy review never satisfies that policy.

Accuracy review is conversational: submitting an answer validates it against the original request and supplied repository evidence, automatically applies a bounded correction, and requests one independent follow-up review. Review findings use the same correction flow. The chief can continue planning and edit or reopen questions throughout. Each interaction permits at most one correction and one follow-up review; a remaining concern is never silently converted into a passing verdict.

Draft envelopes retain `question_progress`, `answer_assessments`, and `accuracy_followup` alongside the existing conversation. Older envelopes default to empty progress and assessments. Assessments retain the submitted answer, effective answer, explanation, and whether it was accepted, factually corrected, assumed, or remains unresolved. Corrected facts cite supplied repository evidence; unsupported defaults belong in assumptions. Explicit preferences cannot be replaced automatically. Optional unanswered questions do not independently fail review when `blocks_approval` is false and a usable `default_answer` is recorded. Consequential unresolved questions still prevent approval.

`POST /api/plan/clarify` accepts `draftId`, `questionId`, `answer`, and the expected `revision`, plus provider/model selection. It returns the updated `draft`, answer `feedback`, `review`, and `review_ready`. Concurrent edits or changed evidence reject stale corrections. Duplicate completed submissions against the same revision do not spend another provider session. Provider failures retain the submitted answer and saved plan with retry state. `POST /api/plan/question-progress` saves unfinished answer text without changing the plan revision or its review binding. The browser also saves input locally immediately, so a reload need not wait for that request.

Both endpoints accept `target: "candidate"` for questions on proposed changes. Their progress, assessments, and review stay on the pending candidate. Checking an answer never applies that candidate or grants approval readiness to the saved plan; applying proposed changes remains explicit and requires a fresh review of the saved artifact.

“Passed” means the artifact met its declared structure and the configured reviewer found no blocking issue. It is not a guarantee of correctness, a claim that checks ran, or authorization to execute work.

GitHub, Jira, and Azure intake records preserve the remote identity and revision as source context when a task is sent to Plan Studio. Imported work is blocked from execution until its source task receives an approved Plan Studio accuracy review. The publish preview shows create or update actions; publishing requires a fresh review and explicit confirmation. Existing remote records are checked against their last recorded revision, and successful mappings are saved after each item so a retry does not create duplicates. GitHub publishing uses `GITHUB_TOKEN`; Azure uses the configured `intake.azure` project and its `token_env` (default `AZDO_PAT`).
