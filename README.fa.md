# Agent Trust Ladder — راهنمای فارسی

>[English full guide: GUIDE.md](GUIDE.md) · [English README: README.md](README.md)

یک اپراتور مهندسیِ مبتنی بر شواهد برای ایجنت‌های کدنویسی — یک اسکیل که در **هر نقطه از پروژه**، به نسبت نیازت، فقط همان بخش را اجرا می‌کند.

ایجنت‌ها اجرا را ارزان کرده‌اند؛ گلوگاه جدید **تأییدِ انسانی در مقیاس خروجی AI** است. این اسکیل هر مرحله از کار را به یک **حکم اعتماد (Trust Verdict)** با شواهد واقعی ختم می‌کند:

> **چه چیزی تغییر کرد؟ چرا؟ چه چیزی ممکن است بشکند؟ اثرش روی چه چیزهای دیگری است؟ به هدف رسیدیم؟**

## یک ورودی هوشمند

اگر نمی‌خواهی خودت بین اسکیل‌ها انتخاب کنی، از `$atl <درخواست>` استفاده کن. ATL وضعیت واقعی پروژه، نوع کار، ریسک و کیفیت feedback loop را می‌سنجد؛ سپس یک playbook اصلی و فقط skillهای ضروریِ موجود را از ATL، PStack و مجموعهٔ Matt Pocock route می‌کند. نبودن یک dependency را پنهان نمی‌کند و به fallback بومی ATL برمی‌گردد.

~~~text
$atl باگ timeout پرداخت را ریشه‌یابی کن و با شواهد واقعی ثابت کن
~~~

قبل از کار مادی، یک Workflow Manifest کوتاه نشان می‌دهد: outcome، نیاز مشاهده‌شدهٔ پروژه، playbook، dose/risk، مسیر skillها، gateها و شرط توقف.

### فقط مسئله را بگو؛ مسیر را ATL انتخاب می‌کند

لازم نیست بدانی الان به frame، spec، plan، implementation، verify، code review، UI review یا audit نیاز داری. مشکل یا هدف را با زبان خودت بنویس؛ ATL وضعیت پروژه و شواهد موجود را می‌خواند و مسیر درست را انتخاب می‌کند:

| چیزی که می‌دهی | چیزی که ATL انتخاب می‌کند |
|---|---|
| ایده یا issue مبهم | اول frame/specify تا ایجنت رفتار را از خودش اختراع نکند |
| رفتار مشخص ولی بدون نقشهٔ کد | specify و بعد plan روی repository واقعی |
| پلن تأییدشده | implement با حلقهٔ تعمیر و verify |
| کد یا artifact آماده | verify با چک‌هایی که واقعاً اجرا می‌شوند |
| diff، PR، merge یا session طولانی ایجنت | audit/review روی کار موجود، نه اجرای کورکورانهٔ مسیر greenfield |
| مشکل صفحه یا interaction | UI review روی render، state، viewport و input واقعی |
| production، auth، build، package، deploy یا سرویس خارجی | contract ledger و شواهد consumer/runtime |
| تغییر کوچک و isolated | Direct dose و چک متناسب، بدون مراسم اضافه |

مثلاً همین مقدار کافی است:

~~~text
$atl بعد از انتخاب فروشگاه، UI برمی‌گردد به فروشگاه قبلی
~~~

ATL خودش بررسی می‌کند که مشکل فقط UI است یا یک باگ cross-layer در persistence؛ مسیر payload تا نتیجهٔ قابل‌دیدن کاربر را trace می‌کند، compatibility و حالت‌های منفی را می‌سنجد و failure اصلی را دوباره مشاهده می‌کند—نه اینکه فقط typecheck بگیرد.

ATL فقط وقتی از تو سؤال می‌پرسد که تصمیم واقعاً انسانی باشد: intent محصول، اجازهٔ تغییر برگشت‌ناپذیر، دسترسی production، پذیرش ریسک یا یک قرارداد خارجی که قابل مشاهده نیست.

## نصب

~~~bash
npx skills add depie99/Agent-Trust-Ladder --all
~~~

یا همهٔ پوشه‌های داخل `skills/` را در پوشهٔ اسکیل‌های ایجنت خودت کپی کن (`.claude/skills/`، `.agents/skills/`، `.codex/skills/`، …). در Codex هر بخش یک اسکیل مستقل است؛ `/atl-*` فقط adapter اختیاری Claude Code است.

اسلش‌کامندها (اختیاری، برای Claude Code): فایل‌های `commands/*.md` را در `.claude/commands/` بگذار.

## کنترل دوز — ضد مراسمِ اضافه

| دوز | کی؟ | چی می‌گیری؟ |
|---|---|---|
| **Direct** | کارِ کوچکِ قابل‌برگشت (تایپو، متن، کامنت) | بدون آرتیفکت؛ یک خط برنامه، انجامش بده، دیف را نشان بده |
| **Standard** | فیچر یا باگ‌فیکس معمولی | بریف → اسپک سبک → پلن با تسک‌ها → خلاصهٔ شواهد (هر کدام یک صفحه) |
| **Critical** | احراز هویت، پرداخت، مایگریشن، production، چند-سرویسی | اسپک کامل + بستهٔ شواهد + گیت‌های تأیید انسانی |

## ۸ ورودی (Mode)

| کامند | برای |
|---|---|
| `$agent-trust-ladder` | router: خودش تشخیص می‌دهد کجای کار هستی و همان بخش را اجرا می‌کند |
| `$atl-bootstrap` | شناخت پروژهٔ موجود: دستورهای واقعی، مرزها، قواعد واقعی (بدون اختراع) + پالیسی اعتماد اولیه |
| `$atl-frame` | ایدهٔ مبهم → بریف محدود؛ یک راند سؤال با پیشنهاد پیش‌فرض؛ تعیین دوز |
| `$atl-specify` | رفتار قابل‌مشاهده + مثال‌های پذیرش؛ تا تأیید صریح انسان جلو نمی‌رود |
| `$atl-plan` | تحلیل اثر، pre-mortem، تسک‌هایی که هرکدام دستور verify خودشان را دارند |
| `$atl-implement` | حلقهٔ خودتصحیحی با بودجهٔ تعمیر؛ هرگز تست را برای سبز شدن تضعیف نمی‌کند |
| `$atl-verify` | اجرای کوچک‌ترین مجموعهٔ راستی‌آزمایی معتبر + حکم اعتماد ۵ سؤالی |
| `$atl-audit` | «ایجنت ۵۰۰ فایل را عوض کرد — امن است؟»؛ verdict فقط-خواندنی روی دیف/PR موجود |
| `$atl-adr` | ثبت تصمیم معماری: آیا ADR لازم است؟ ثبت گزینه‌ها، پیامدها، lifecycle و fitness evidence |
| `$atl-trust` | نردبان L0–L7: چه کارهایی ایجنت بتواند خودش انجام دهد؟ با گیتِ ۹ سؤالی |

## از کجا شروع کنم؟

~~~text
$atl-bootstrap                                  ← اولین بار روی هر پروژهٔ موجود
$atl-frame کاربرها فیلترهاشان گم می‌کند          ← ایدهٔ مبهم
$atl-audit PR #482                              ← بررسی یک دیف بزرگ
~~~

بدون کامند هم می‌شود: بگو *"این دیف را audit کن"* یا *"این ایده را frame کن"* — خودش مسیر درست را پیدا می‌کند.

## در پروژه‌ات چه چیزی ساخته می‌شود؟

~~~text
.trust/
  project-brief.md   # قواعد واقعی پروژه (مشابه constitution)
  trust-policy.md    # سقف استقلال ایجنت برای هر کلاس کار
  ledger.md          # دفتر ثبت: verdictها، شکست‌ها، تغییرات اعتماد
  specs/001-.../     # بریف، اسپک، پلن، شواهدِ هر تغییر
~~~

## چرا با بقیه فرق دارد؟

- **دوز، نه دگم** — کارِ کوچک اصلاً وارد مراسم نمی‌شود.
- **شواهد به‌جای اعتماد‌به‌نفس** — تیک سبک و توضیح قاطع، اثبات نیستند.
- **استقلالِ ایجنت، به‌ازای هر کلاس کار** — داکیومنت و پرداخت نردبان‌های جدا با شواهد جدا دارند.
- **شکست پنهان نمی‌شود** — چک‌های اسکیت‌شده جدا گزارش می‌شوند.
- **مسئله را بده، workflow را نه** — ATL ورودی واحد است و خودش specialist مناسب را انتخاب می‌کند.
- **خروجی خوب یعنی شواهد خوب** — commit، merge، typecheck و build به‌تنهایی اثبات رفتار runtime نیستند.
