Tracking plan: #14.

## Outcome
After a task, the developer can inspect what changed, which acceptance behaviors were observed, what remains unresolved and whether the evidence still matches the final files. Reuse Review changes and existing delivery gates; do not build a new dashboard.

## Scope and existing foundation
Compose a concise receipt from source revision, accepted task contract, final content identity, changed-file summary, diff/snapshot references, verifier and instruction provenance, check results, review findings/dispositions, run attempts and resource coverage. Store large artifacts separately and link their contents with explicit availability/freshness. Missing artifacts or unknown usage must be visible.

## Control Plane
Extend the existing task change-review/evidence view with the receipt and a short decision summary. For a UI change, link/view actual before/after captures and observed behavior where applicable; for backend work, show relevant runtime readback or test evidence. A contract statechart cannot stand in for execution evidence. Existing integrated delivery gates remain authoritative.

## Skills-only
Generate the same receipt as Markdown plus machine-readable JSON in project-local evidence, with relative artifact links and standard diff/snapshot output. The reviewer can inspect a complete package without the Control Plane service. Skill instructions require the same freshness, unresolved-finding and completion checks as the UI.

## Acceptance
- [ ] An Azure task receipt traces source -> acceptance -> changed files -> checks/review -> final content through both entry points.
- [ ] Editing an affected file, verifier or relevant policy after a check makes that evidence stale and prevents an unconditional completion verdict until rechecked.
- [ ] Missing screenshots/artifacts, failed checks and open blocking findings are explicit; a screenshot of an opening page alone cannot verify a changed interaction.
- [ ] Findings have stable IDs, severity/confirmation, affected requirement/path/revision, evidence and disposition. Fixed claims need a relevant recheck; rejected/risk-accepted findings require a reason and authorized decision.
- [ ] A small UI fixture and a non-UI fixture yield usable receipts; the rendered UI shows the actual artifact, its attribution and stale/blocked state.
- [ ] The portable receipt and UI projection agree on verdict and unresolved decisions. Neither fabricates a PR, deployment, usage estimate or independent review.
