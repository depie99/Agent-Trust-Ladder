## Outcome
The developer starts one finite evening batch of ready Azure tasks, leaves it running, and returns to a terminal receipt for every selected task. Known safe failures receive bounded repair; an unresolved blocker cannot monopolize the whole night or masquerade as success.

## Scope and existing foundation
Build on supervisor-runner, existing settled-task exclusion, remaining-time propagation, workspace isolation, preparation journals, recovery limits and usage records. The existing supervisor exits when idle. A persistent daemon, periodic polling and a new scheduling platform are outside this slice.

Start with a sequential batch (concurrency 1), fixed item list and approved wall-time/attempt/session limits. Repair only the affected work/checks; preserve unrelated verified work. Keep a small durable failure signature and attempt record so restarting cannot reset repair limits. At the deadline stop new work and reconcile any in-flight process according to the host's actual capability.

## Control Plane
Expose the existing run/supervisor controls with explicit batch scope, limits and readiness summary. Provide progress, stop reason, recovery state and a morning summary linking #18 receipts. Reconcile lease/process/artifact state before resuming; an unknown external effect requires reconciliation, not blind replay.

## Skills-only
Provide a bundled portable sequential runner or host-neutral resume/checkpoint helper using the same rules and receipt format. An interactive host may launch it directly or use an already authorized host scheduler. Persist run/attempt records locally so a new session can resume. Declare that the machine/host must remain available. Never claim the skill itself supplies durable compute, OS isolation, a scheduler or enforceable token caps that the host lacks.

## Acceptance
- [ ] A three-task deterministic batch includes one clean success, one known repairable failure and one genuine blocker; independent work finishes and every task has a terminal or explicitly interrupted status.
- [ ] Inject a provider interruption, stale lease, repeated no-progress failure and process restart; no duplicate completed work or automatic repetition of an uncertain side effect occurs.
- [ ] Deadline and retry limits survive restart; settled/no-progress work is not repeatedly dispatched in the same or resumed run.
- [ ] Credentials missing at preflight are reported once with a clear recovery action; bounded repair does not invent authority or install tools.
- [ ] Scope, time and attempt limits are mechanically enforced where supported. Actual token usage is reported with coverage; missing telemetry remains unknown. Provider spend limits are labeled unenforceable when the host cannot enforce them.
- [ ] Runtime and portable runs produce equivalent outcomes/checkpoints for shared failure fixtures. A malformed/forged checkpoint cannot grant completion or erase attempt accounting.
- [ ] After resumption, the final composed files are reverified where affected, and the morning summary links current receipts and the smallest remaining human decision.
