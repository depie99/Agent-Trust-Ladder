## Outcome
Ship a first usable Azure-first delivery path with observed evidence from both surfaces. A developer can install the skills alone or use Control Plane, run a small authorized batch and review the resulting files, behavior, checks and blockers without guessing what finished.

## Pilot and scope
Use one Azure project, one repository and one stack chosen during readiness. Freeze two or three contained Azure tasks with observable acceptance behavior. Include a small UI interaction if visual changes are part of the selected application. Execute comparable UI and skills-only runs in separate isolated workspaces from the same starting content; do not execute one run's already-fixed output in the other. Record host/model/tool versions and differing capabilities.

Live provider runs need the user's concrete task/environment and bounded run authority. Issue publication alone does not authorize paid calls, repository publication, merge/deployment or Azure writeback. Deterministic fixtures can be completed while live access is unavailable; mark the live gate OPEN instead of substituting mock evidence.

## Control Plane
Verify the rendered preview -> readiness -> queue/run -> change review -> delivery journey, including stale/missing evidence and one blocked task. Link redacted before/after captures and final task receipts. Use disposable test state for automated browser journeys.

## Skills-only
Install the packaged ATL skills/helpers into an independent fixture/project. Complete the same readiness, intake, execution, bounded recovery and receipt review without the Control Plane service or shared manager state. A fresh host session must understand the checkpoint and remaining decisions from files.
